## 0. 项目背景（一句话）

`ai-trader-btc` 是一个 AI 驱动的 BTC 交易系统：Nest.js 后端 + Vite/React/antd 前端 + `packages/shared`，
已接入 Binance/OKX 双交易所适配器，支持真实行情秒级推送、K 线增量渲染、统一风控下单。

当前 Agent 默认配置：`decisionIntervalSec=300`、`positionPct=0.1`、`minConfidence=0.6`、`minOrderIntervalSec=60`，
运行在 **testnet（测试网）** 模式，`enabled=false`（默认不自动交易，需人工开启）。

## 2. 关键问答详录

### Q1：两条链路要完全独立、互不干扰，通过开关打开

**用户原意**：AI 链路（LLM 决策）和纯策略链路（技术指标）要彻底解耦，用户能通过一个开关选择走哪条，
且一条挂了不能偷偷影响另一条。

**讨论要点**：
- 现状问题：纯策略其实是 `AgentEngine.fallbackDecision()` 这个**私有方法**，只在 LLM 失败时触发，
  不是独立通道；而且 `degradedAction='hold'` 会连"主动关 LLM 想跑纯策略"也一起挡住，永远不下单。
- 开关职责混乱：`LLM_ENABLED`（全局环境变量）、`degradedAction`（降级保护）、`enabled`（总开关）
  三个配置语义纠缠，无法表达"用哪条链路"。
- 结论：新增顶层三态开关 `decisionLane`，彻底取代混乱控制方式。
  关键隔离点——`strategy` 链路下 `LlmClient` 完全不参与（不读 key、不发请求、零 token 成本）。

→ 落地见计划 §2.1、§2.2、§2.3（链路分派图）

---

### Q2：回测要不要加进计划？

**用户**："对，回测也要加进去。"

**讨论要点**：
- 原想把回测放后期，但策略改动（修复缺陷、新增策略）若没有回测，只能靠 testnet 实盘试错——既慢又无法量化收益。
- 结论：**回测引擎提前到阶段 2**，放在"策略框架迁移（阶段1）"之后、"修复缺陷/改参数（阶段3）"之前。
- 回测复用已有能力：`StrategyService`（纯函数可回放）、滑点建模（`slippageBps`）、持仓推导（`computePosition`）。
- 必须能回答一个核心问题：**这个策略跑不跑得赢"直接持有 BTC"（buy&hold）**——即相对基准的超额收益。

→ 落地见计划 §阶段2、§八（回测验收标准）

### Q3：比特币量化交易如何做架构更好？策略与 AI 隔离还是结合？

**用户**：想知道从量化架构师视角，两者该怎么摆。

**核心论证（回答）**：
1. **先看能力边界**：
   - 量化策略 = 确定性规则：精确、可回测、可证伪、亚毫秒、零边际成本；弱点是只能识别见过的模式，参数易过拟合，市场状态切换时**连续亏损（可预测）**。
   - LLM = 概率性推理：能处理非结构化信息、理解"这次不一样"；弱点是不可回测、不可复现、会幻觉、延迟大、有成本，失败**不可预测**。
   - 关键差异：策略的失败可预测（能回测出最大回撤），AI 的失败不可预测。这决定了它们该放在哪一层。

2. **为什么"AI 直接下达买卖指令"是高风险架构**（当前项目现状）：
   - 不可回测 → 每次调 prompt 都是在真金白银上做实验，且无法归因
   - 不可复现 → `temperature>0` 同样输入不同输出，出问题无法复盘
   - 延迟与成本 → 决策频率被锁死在分钟级以上

3. **为什么纯策略也不够**：技术指标 alpha 衰减严重（RSI/MACD/布林带已是公开共识），无法处理叙事驱动行情（ETF 资金流、监管、交易所暴雷），而这些不在 K 线里。

4. **推荐架构：分层裁决（Layered Adjudication）**
   ```
   Layer 4 风控层    硬约束，规则实现，不可绕过，AI 不得参与
   Layer 3 执行层    策略规则，确定性，可回测，AI 不得参与
   Layer 2 信号层    指标计算，确定性，可回测
   Layer 1 上下文层  ← AI 唯一的参与位置
   Layer 0 数据层    行情/新闻/链上/资金流
   ```
   **AI 输出"元参数"而非买卖指令**：市场状态、风险偏好、新闻情绪、持仓定性评估。
   策略接收元参数作为**输入条件**，但执行逻辑仍是确定性规则。

5. **四个收益**：可回测（AI 判断可冻结为历史快照）、可归因（energy 是 AI 错还是策略错）、
   降级安全（AI 挂掉用中性默认参数继续跑，不停摆）、成本可控（AI 调用可降至小时/天级，策略执行仍维持分钟级，两者解耦）。

6. **重要实践建议**：让 AI 做研究而不是做交易。用 AI 分析历史找"策略失效场景"→固化成规则→回测验证→上线执行规则。AI 价值被固化成可回测规则，而非每次依赖实时推理。

→ 落地见计划 §2.4.1 ~ §2.4.7

### Q4：AI 输出市场状态/风险偏好/新闻情绪，然后根据此切换不同策略去运行吗？

**用户**：顺着分层裁决，问 AI 上下文具体怎么作用到策略。

**回答**：AI 元参数作用到策略有三种方式：

| 方式 | 机制 | 评价 |
|---|---|---|
| **A 策略切换** | regime → 选不同策略运行 | 直观但离散突变、边界抖动、切换时持仓归属不清 |
| **B 参数调节** | 元参数 → 映射 `positionPct`/`minConfidence`/止损宽度 | 连续平滑、策略逻辑不变、可回测（**推荐为主**） |
| **C 条件过滤** | 极端情况一票否决（如情绪极端负面禁开新仓） | 最安全，AI 日常不介入（**兜底用**） |

推荐组合：**B 为主、A 为辅、C 兜底**。

为什么 B 优先于 A：策略切换是离散的，AI 判断在趋势/震荡边界反复横跳会导致策略反复切换、反复被止损打脸；
参数调节是连续的，同样抖动只造成参数小幅波动。

→ 落地见计划 §2.4.8

### Q5："那就是按照调节参数的方式去，策略还是一个，是这个意思吗？"

**用户**：澄清确认——是不是"一个策略 + 参数调节"。

**回答：是，这正是推荐 MVP。** 需要区分两个正交维度：

| 维度 | 由谁决定 | 频率 | 含义 |
|---|---|---|---|
| 用哪个策略（逻辑） | 人工静态选，或 regime 高置信才切换 | 低（天/周级甚至固定） | 策略的**逻辑结构** |
| 策略参数怎么调（强度） | AI 元参数实时映射 | 高（分钟级） | 这个逻辑的**激进度** |

示例：
```
人工选定：trend_following（逻辑固定，可回测）
    ↓
AI 输出：trendStrength=0.72, aggression=0.8, newsSentiment=+0.3
    ↓
映射：positionPct   = 0.1 × 0.8 = 0.08
      minConfidence = 0.6 + (1 - 0.3) × 0.1 = 0.67
    ↓
执行：还是 trend_following，但这次用 0.08 仓位、0.67 门槛出手
```

**但参数调节有边界**：参数只能表达同一逻辑的强弱，不能表达逻辑切换。
趋势跟踪参数再怎么调也调不出均值回归（那是相反赌注）。所以：
- 只做趋势跟踪 → 一个策略 + 参数调节完全够用（推荐 MVP）
- 想震荡市做均值回归 → 必须引入第二个策略（逻辑相反，参数调不出来）

**结论**：先落地"一个策略 + 参数调节"，用上下界法（§2.4.10）验证 AI 层是否有增量价值；
有效后再考虑策略家族。反过来做会一开始就背负多策略复杂度。

→ 落地见计划 §2.4.8.1

## 4. 给新智能体的快速上手建议

1. **先读 `docs/decision-lanes-plan.md`** —— 这是落地依据，结构清晰、可直接对照实施。
2. **再读本文档 §2** —— 理解每个设计决策背后的"为什么"，避免改着改着回到旧架构。
3. **核心心法**：AI 不做执行决策，只做上下文判断；策略不做全市场判断，只做精确执行。
   参数调节优先于策略切换；先验证一个策略+调参的 MVP，再谈多策略。
4. **实施顺序严格按阶段 0→6**，每阶段独立验收、独立回滚；阶段 2 回测先行。
5. **不要破坏已验证的 P0/P1 基座**；新增链路开关时确认 `strategy` 链路零 LLM 依赖。
6. **未提交的工作**（`git status` 显示 README 改动 + docs/ 未跟踪）请先与新用户确认提交策略，
   尤其注意 `.env` 密钥不要误提交。
