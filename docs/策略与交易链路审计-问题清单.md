# 策略与交易链路审计 · 问题清单

> 视角：比特币合约量化策略研发。
> 范围：策略层（`apps/server/src/strategy/*.strategy.ts`、`packages/shared`）、回测撮合层（`apps/server/src/backtest/**`）、实盘执行层（`apps/server/src/futures/**`、`apps/server/src/account/**`、`apps/server/src/exchanges/**`）。
> 对标：Freqtrade / Jesse / Hummingbot / Nautilus Trader / QuantConnect Lean / vectorbt / CCXT 的主流工程实践。
> 说明：本文只列"问题"，不含改动。每条给出 **现象 → 证据 → 根因 → 业界对照 → 影响** 五段，便于逐条核实与排期。

## 🔴 P0-1　实盘周期与回测/策略声明周期不一致（最致命）

**现象**：策略在回测里按声明周期（如 Donchian 的 4h/1h）验证通过并上架，但**实盘运行时喂给它的是 1m K 线**，信号含义完全走样。

**证据**：
- 实盘上下文构造 `apps/server/src/strategy/strategy-runner.service.ts` 的 `buildContextFor()`：
  ```ts
  const candles: Candle[] = this.market.getCandles(symbol, '1m', CONTEXT_CANDLE_LIMIT);
  ```
  周期**硬编码 `'1m'`**，与策略 `manifest.capabilities.timeframes`、平台配置、回测周期都无关。
- `inferIntervalMs(ctx)` 从相邻两根 K 线时间差推周期 → 实盘恒为 60_000ms（1m），回测为 `TIMEFRAME_MS[config.interval]`（如 4h=14_400_000ms）。
- 策略参数全部以"根数"为单位（`breakoutLookbackBars=20`、`exitLookbackBars=15`、`maxHoldBars=240`、`trendMaPeriod=30`、`regimeEmaSlow=50`）。在实盘 1m 下：入场通道=20 分钟、时间止损=240 分钟=4 小时；在回测 4h 下：入场通道=80 小时、时间止损=40 天。**同一参数、两种世界**。
- ATR 同样分裂：`ctx.atr` 在实盘由 1m K 线算（值极小），回测由 4h 算（值大）→ 吊灯距离、网格间距 `gridStep`、波动率定标数量全都按错误波动率缩放。
- `donchian-breakout/manifest.json` 的 `riskNotes` 明确写"5m 噪声过大不建议"，`capabilities.timeframes=["1h","4h"]`；而记忆库结论"Donchian 5m 失效、4h 有效"。实盘却跑在比 5m 更细的 1m 上——**直接在生产环境启用了已被判定失效的周期**。

**根因**：runner 构造 ctx 时没有把策略声明的周期作为取数周期；`MarketService` 虽然为所有周期（含 4h）都维护了 K 线（`syncDerivedIntervals`），但 runner 弃之不用，一律取 1m。回测走 `config.interval`，实盘走固定 1m，二者无统一来源。

**业界对照**：Freqtrade / Jesse / Nautilus 的第一设计约束就是"回测与实盘共用同一个 `timeframe` 配置项，策略只面向该周期的 OHLCV 编写"；细粒度成交用 `timeframe_detail` 显式声明，绝不隐式换周期。本项目的缺陷正是"周期没有单一真值来源"。

**影响**：所有以根数为单位的策略在实盘的行为与通过闸门时**不是同一个策略**。这是"回测好看、实盘变形"的头号来源，优先级最高。

## 🔴 P0-2　上架闸门/研究全跑无强平的 vectorized 引擎，杠杆爆仓在量具中隐身

**现象**：三层防过拟合入口（walk-forward、CPCV、DSR、sweep、regime、Monte Carlo）全部基于 `vectorized-v1`（`SimBroker`），而该引擎**没有任何保证金/强平模型**；带强平的 `event-driven` 引擎未接入闸门。

**证据**：
- `apps/server/src/backtest/backtest.service.ts`：`const ENGINE_VERSION = 'vectorized-v1'`；`walkForward` / `runResearch` / `sweep` 均调用 `runBacktestOnCandles`（`apps/server/src/backtest/backtest-runner.ts`），使用 `SimBroker`。
- `SimBroker`（`apps/server/src/backtest/sim-broker.ts`）的 `equity()` 可为负且从不强制平仓；只有 `event-driven/event-broker.ts` 实现了 `markPrice → equity < maintMargin×notional → liquidate`。
- 更危险的是闸门 rationale 自认："定稿引擎：vectorized-v1 与实盘 1m 同粒度即本阶段定稿引擎；event-driven L2/冲击模型为设计范围外"（见 `hasPassingResearch` 的 `engine_v2` 判据注释）——这句 rationale **建立在 P0-1 的错误假设之上**（它以为回测=实盘同粒度，实则回测多为 4h、实盘为 1m），等于用一个错误前提论证"不需要 event-driven"。
- 马丁网格 `maxLayersPerSide=4`、`leverage=10`、`netExposureCapPct=0`（敞口不限），是典型尾部风险策略；在 vectorized 里永远不会爆仓 → DSR/OOS 回撤指标看不到真实破产概率。

**根因**：把"保真度更高的 event-driven"当成研究范围外，让决定生死的调优/闸门运行在结构上无法显示爆仓的简化引擎上。

**业界对照**：Nautilus Trader / Lean 的账户模型内置 margin、liquidation、fill model，回测即会强平；Freqtrade 有 `trailing_stop`/`stoploss_on_exchange` 与账户清算近似。用无强平引擎为高杠杆策略调参，在主流框架里属于反模式。

**影响**：高杠杆/马丁类的"过闸门"结论可信度低——量具本身看不见破产，回撤下界被系统性美化。

## 🔴 P0-3　波动率定标的权益口径，回测≠实盘

**现象**：同一个入场信号，回测和实盘用 `computeRiskScaledQty` 算出的下单数量不同，破坏"策略一行不改即可回放"的 parity 前提。

**证据**：
- `computeRiskScaledQty({ equity: ctx.availableMargin, ... })`（`packages/shared/src/position-sizing.ts`）以传入的 `equity` 为分母做风险预算定标。
- 实盘：`ctx.availableMargin = safeAvailableMargin() = trading.getAvailableMargin()`，其定义是 `balances.find(b => b.asset==='USDT').free`——**可用保证金余额**（已扣现有持仓占用、不含浮动盈亏）。
- 回测：`ctx.availableMargin = broker.equity(mark)`（见 `backtest-runner.ts` / `event-driven/runner.ts`）——**总权益**（本金+已实现+浮动+资金费），且不含"已被占用保证金"的概念。
- 两者语义不同：账户有 1000U、已开一单占用 500U 时，实盘 `availableMargin≈500`、回测 `equity≈1000+浮盈`。同一信号下 notional 直接差一倍。

**根因**：`availableMargin` 字段名在 SDK 里既是"可用保证金"又被回测当"总权益"填充，契约层没有把两者区分开（`types.ts` 注释写"可用保证金（USDT）"，但回测填的是 equity）。

**业界对照**：Freqtrade 定标基于 `stake_amount`/`tradable_balance_ratio`/`free_open_trades` 的显式余额语义；vectorbt/Nautilus 明确区分 equity 与 free margin，不会在同一个变量里两套填法。

**影响**：仓位大小的回测/实盘不可比，叠加 P0-1 后实盘数量偏差被进一步放大。

## 🟠 P1-4　DSR 闸门阈值 0.5，多重比较校正形同虚设

**现象**：过拟合核心判据 Deflated Sharpe 的放行线只有 0.5，几乎等于"抛硬币"。

**证据**：
- `backtest.service.ts`：`const GATE_DSR_MIN = 0.5`。
- `donchian-breakout/manifest.json` 的 `backtestRef.dsr = 0.7285`，`verdict = "pass"`——DSR 0.73 含义是"约 27% 概率这份夏普只是挑选偏差"，却判过。
- 对比 `packages/shared`/`research/deflated-sharpe.ts` 自身文档：`threshold 默认 0.95`，并直接引用 Bailey & López de Prado (2014)。代码实现的默认值是 0.95，闸门实际用 0.5，**自己写的标准自己不用**。
- `GATE_OOS_SHARPE_MIN = 0`（OOS 年化夏普只要非负即可），同样偏松。

**根因**：门槛常量与研究模块引用的学术标准不一致，且未记录"为何降到 0.5"的留痕（overrideReason 机制存在但未用于阈值本身）。

**业界对照**：主流研究实践 DSR 门槛取 0.90~0.95；低于此即视为可疑。

**影响**：闸门对过拟合的拦截力被削弱，P0-2 的失真指标又直接喂给这个已偏松的闸门，两层叠加。

## 🟠 P1-5　Sharpe 基于"稀疏已实现日"的美元序列，系统性高估

**现象**：`computePerformance` 的夏普既不是收益率口径，也只统计"当天有平仓"的日子，非交易/无平仓日被整段丢弃。

**证据**：
- `packages/shared/src/metrics.ts`：日聚合 `daily` 这个 Map 只对 `b.closedAt !== null` 的篮子写入，**没有任何"当日无交易=0 收益"的补零**；随后 `sharpeRatio(rets)` 在这条稀疏序列上算 `mean/std × √365`。
- 序列里每个值是"当日绝对美元盈亏"，`mean/std` 是美元量纲 → 是"dollar-Sharpe"，随本金缩放而变，跨策略/跨资金不可比。
- 一个每周只平一次、其余 6 天空仓的策略，其夏普只用那 1 天样本估计，方差被严重低估 → 夏普被抬高。
- 回测 `BacktestMetrics.sharpeRatio` 直接取 `basketMetrics.sharpe`，所以回测/实盘"同口径"= **同一个偏差口径**。

**根因**：以"篮子已实现"为评价单元对马丁是对的，但把它直接当日收益序列算 Sharpe 混淆了"回合数稀疏"与"时间序列收益"。

**业界对照**：Freqtrade/vectorbt/Lean 的 Sharpe 一律基于**逐期净值收益率序列**（含空仓期 0 收益）并按周期年化；本项目回测的 `equityCurve`（`backtest-runner.ts` 逐 bar 记录）本身就有完整净值，本可直接用它算 Sharpe，却用了篮子稀疏序列。

**影响**：所有策略的夏普、以及依赖 per-bar Sharpe 的 DSR，均偏乐观。

## 🟠 P1-6　资金费率默认为 0，跨 8h 持仓的成本不计

**现象**：默认回测不计资金费，趋势/马丁这类持仓动辄数天的策略，其收益被高估。

**证据**：
- `SimBroker.accrueFunding()`：`if (!(this.cfg.fundingPctPer8h > 0)) return;`——为 0 直接跳过。`backtest.types`/config 默认 `fundingPctPer8h` 常为 0。
- 报告目录里大量 `trend_following`/`donchian`/`martingale_grid` 结果未必显式设定了资金费。
- 实盘侧资金费真实发生（`income.service`/结算），但调优/闸门用的 vectorized 侧默认忽略 → 又是回测≠实盘。

**根因**：资金费被做成可选项且默认关。

**业界对照**：Freqtrade 合约回测 `use_funding_fee`（默认 True）、Lean/Nautilus 强制计入 funding。主流默认是"开"而非"关"。

**影响**：净收益被高估，尤其对长持仓与拥挤方向（多头正费率时成本最高）。

## 🟠 P1-7　撮合保真度：vectorized 单根 high/low 判 STOP、固定 bps 无冲击

**现象**：主调优引擎的成交价假设偏乐观，且没有成交量/冲击模型。

**证据**：
- `sim-broker.ts` `beginBar()` 用 `bar.high/low >=/<= stopPrice` 判定 STOP 触发，成交价取 `stopPrice`（跳空时用 open 修正）。一根 K 线内若先插针穿止损再回到有利位，引擎无法分辨穿越次序 → 按"恰好 stopPrice 成交"这一最有利的假设记账。
- 市价单恒"下一根开盘成交"（`fillConvention='next-open'`），滑点是固定 `slippage` bps，与下单量无关。
- `event-broker.ts` 顶部注释自认："待 P1b 补：L2 队列 / VWAP 吃深度 / 冲击平方根律 / maker 分档 / latency 20ms"。即项目自己也承认真实成交模型尚未落地。

**根因**：调优/闸门选择了简化引擎，简化引擎的成交假设对突破/止损类策略天然有利。

**业界对照**：Nautilus/Lean 用逐笔或订单簿撮合，freqtrade `timeframe_detail` + orderbook 处理 intrabar。

**影响**：Donchian/Turtle 这类"追突破+吊灯止损"的策略，其回测收益对 intrabar 失真最敏感，实盘滑点/穿针损失通常更大。

## 🟡 P2-8　出场状态仅在内存，服务重启即丢失

**现象**：策略的吊灯止损位、开仓时间、冷却时刻、篮子追踪止盈峰值都是内存 Map/字段，进程重启后被清零，而仓位由 `adoptExisting` 接管——于是"仓还在、出场逻辑记忆没了"。

**证据**：
- `donchian`/`trend`：`chandelierStops`、`entryTimes`、`lastCloseAt` 为实例字段，`onStart()` 全部 `clear()`/置 0。
- `martingale`：`basketPeakPct`、`firstMarketAt` 同理在 `onStop/onStart` 重置；追踪止盈峰值丢失 → 重启后可能过早平或过晚平。
- 重启恢复走 `resumeIfShould()` + `startInstance(..., { adoptExisting: true })`，会接管 Lot，但**不会重建这些出场状态**（吊灯回退到"以当前 mark 重新播种"，`lastCloseAt=0` 冷却失效）。

**根因**：策略是有状态对象，但状态只活在一个进程的内存里，没有落库/快照。

**业界对照**：成熟框架把关键持仓态（trail 峰值、入场时间、保护期）持久化或可从成交重建，保证重启幂等。

**影响**：pm2/发版重启会让出场行为发生不可预期变化，实盘与"连续运行的回测"不一致。

## 🟡 P2-9　donchian / trend / mean_reversion 平仓未查 `hasPendingClose`

**现象**：马丁在篮子出场前用 `hasPendingClose` 做了在途去重，但趋势族三个策略的逐 Lot 平仓循环没有这道闸。

**证据**：
- `martingale-grid.strategy.ts` `checkBasketExit()`：`const inflight = ctx.openLots.filter(l => l.hasPendingClose)...; if (inflight>0) return true;`——有防护。
- `donchian/trend/mean-reversion` 的持仓出场循环里直接 `await exec.closeLot(lot.id, ...)`，未过滤 `lot.hasPendingClose`。
- SDK `StrategyLotView.hasPendingClose` 已提供该字段、注释也写明用途，只是没被这三个策略使用。

**根因**：出场去重不变量只在部分策略实现，未上收到 executor 或统一约定。

**影响**：在途平仓尚未结算的窗口内（tick 节流 800ms、行情驱动），可能反复对同一 Lot 下 reduceOnly 平单，增加冗余下单/失败重试与噪声（平台层 Lot OPEN 校验能兜住一部分，但仍是行为不一致）。

## 🟡 P2-10　指标实现分裂：同名不同公式

**现象**：同一概念在 shared 与各策略里有不同实现，跨策略指标不可直接比较，易埋漂移。

**证据**：
- EMA：`packages/shared/src/indicators/core.ts` 的 `ema()` 以 `values[0]` 播种递推；`mean-reversion.strategy.ts` 内置 `ema()` 以 `SMA(period)` 播种。trend/donchian 用 shared 版，mean-rev 用自带版 → 同周期同数据两值不同。
- RSI：shared `rsi()` 是 Wilder 平滑；mean-rev 内置 `rsi()` 是"Connors 最近 n 期涨跌均值"简单法（且 `avgLoss===0` 时返回 100/50 的自定义分支）。
- ATR：donchian/trend 用平台 `ctx.atr`，martingale 自己 `atrOf(ctx.candles)`（且要求 `candles.length>=20` 否则 0）。
- 注：因为**同一策略**回测与实盘走的是同一份源码，所以单策略 parity 尚在；问题在跨策略口径不统一与重复实现。

**根因**：SDK 提供指标但策略"自带指标"，未强制统一到 shared 内核，也无"指标口径一致性测试"。

**影响**：策略间可对比性、可维护性受损；一旦有人把某策略改用 shared 版指标，信号会静默改变。

## 🟡 P2-11　手续费单一真值为硬编码实测值，取不到真实费即回落

**现象**：全链路兜底费率写死 0.0004，且 maker/taker 不分。

**证据**：
- `packages/shared/src/position.ts`：`export const FUTURES_TAKER_FEE_RATE = 0.0004`（注释："本 demo 账户实测 0.04%，官方标准 0.05%"）。策略出场判定、回测兜底、展示都用它。
- `futures-trading.service.ts`：真实费优先 `/fapi/v1/userTrades`，取不到即 `FUTURES_FEE_BPS` 估算；非稳定币计价（如 BNB 抵扣）直接 `return null` 回落估算。
- 撮合侧一律按 taker 计费：网格 STOP 触发的市价成交按 taker 合理，但若引入限价 maker 被动成交仍按 taker 高估成本（方向相反）。

**根因**：把"某账户某时点的实测 taker"上升为全局常量单一真值。

**影响**：账户费率档位变化、返佣/BNB 抵扣场景下，回测与实盘净收益都会系统性偏离；对"费率是净收益生死线"的合约策略尤其敏感。

## 🟡 P2-12　对账/FIFO 兜底与孤儿 Lot 按 0 盈亏归档，归因可能错配

**现象**：平仓结算存在按 FIFO 猜 Lot、以及"交易所已平但本地按 0 盈亏归档"的兜底路径。

**证据**：
- `futures-trading.service.ts` `syncPendingFills()`：历史无 `lotId` 的平仓单走 `lots.findOldestOpenLot(...)` FIFO 兜底猜最早同向 Lot。
- `lot.service.ts` `reconcileOrphanLots()`：交易所该方向持仓为 0 时把本地 OPEN Lot 置 CLOSED，`realizedPnl = 0`（注释"宁可不算，不要瞎算"）。
- 这些安全阀本身是合理的防御，但会让 `position_lots.realizedPnl` 与交易所真实 income 脱节，而绩效/闸门/熔断都读 `realizedPnl`/篮子。

**根因**：本地 Lot 表与交易所真实实现盈亏之间没有以 income 为权威的定期对账闭环（当前只在能取到 commission 时对齐）。

**影响**：误归档/兜底结算会让已实现盈亏统计与真实账户不完全一致，进而影响闸门留痕数据可信度。

## ⚪ P3-13　平台侧"零风控"与多实例共享账户敞口

**现象**：平台明确不做层数/敞口/杠杆上限/熔断拦截（`futures-trading.service.ts` 注释多处"平台不做风控"），而多实例共享同一个账户的 free margin。

**证据**：
- 每个实例 `openLot` 都按各自 `equity/availableMargin` 定标，但没有账户级聚合敞口守卫；`netExposureCapPct` 默认 0（martingale 不限敞口）。
- 已有 `protection.service.ts` 熔断（连亏/回撤）是"事后停实例、不平仓"，不能防止两个实例同时把账户杠杆叠满。

**业界对照**：Freqtrade 内建 `max_open_trades`、`margins_ratio`、protections（CooldownPeriod/StoplossGuard/MaxDrawdown）作为账户级兜底。

**影响**：多实例并发下的账户级爆仓风险无人兜底（属产品定位取舍，但从策略研发角度应作为已知风险显式声明并加账户级聚合监控）。

## ⚪ P3-14　时间/墙钟语义的引擎差异

**现象**：`ctx.now` 实盘=`Date.now()`、回测=bar 收盘时刻；`cooldownSec` 用墙钟，tick 节流 800ms + 事件驱动。

**证据**：
- `buildContextFor()` `now: Date.now()`；`backtest-runner.ts` `now: bar.time`；`event-driven/runner.ts` `now: ev.bar.time + intervalMs`。
- 策略内 `cooldownSec`、`maxHoldBars*intervalMs` 依赖 `now` 与 intervalMs，跨引擎语义连续但边界（断线补帧、WS 抖动、盘口缺口）会改变实盘的冷却/时间止损触发时刻，而回测是理想整 bar 序列。

**影响**：影响小但属回测/实盘残差来源之一，纳入 parity 测试时应覆盖。

## 建议的修复优先级（只列顺序，不含具体改动）

1. **先修量具的"同物同周期"**：让实盘取数周期 = 策略声明周期 = 回测周期（P0-1），并统一 `availableMargin` 的权益语义（P0-3）。这两条不解决，其余调参结论都建立在流沙上。
2. **让闸门跑在有强平的引擎**：walk-forward/DSR/sweep 至少对高杠杆/马丁类切到 event-driven 或在 vectorized 里补 margin/liquidation（P0-2），并据此重估 `vectorized-v1 即定稿引擎` 这一 rationale。
3. **收紧统计口径**：Sharpe 改用完整逐期净值收益率序列（含空仓期）、资金费默认开启（P1-5/6）；把 DSR 阈值与 `deflated-sharpe.ts` 自己引用的 0.95 标准对齐或在闸门处显式记录降级理由（P1-4）。
4. **补齐健壮性**：出场状态持久化/可重建（P2-8）、趋势族平仓统一 `hasPendingClose`（P2-9）、指标口径上收到 shared 内核（P2-10）、费率改为账户档位真值（P2-11）。
5. **治理类**：Lot 与交易所 income 的定期权威对账（P2-12）、账户级聚合敞口监控（P3-13）。
